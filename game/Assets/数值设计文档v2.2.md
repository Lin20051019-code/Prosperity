## 一、版本沿革：v2.1 → v2.2 决策链

1. **试玩诊断（实机口径 5000 局模拟）**：胜率仅 4-5%；52% 的局峰值繁荣卡在 45-59，14% 卡 80-99（"指数到89上不去"的来源），仅 5% 登顶；危机区时间占用 38%。**根因是 P0 入账 bug（见第三节），不是 v2.1 数值本身**。
2. **修复后的选择**：仅修 bug 胜率会回到 35-43%（约 2-3 局赢 1 局）。策划拍板新验收哲学：
   - **赢要珍贵**：4-6 局赢 1 局（胜率 17-25%），胜利含金量高
   - **输多赢少有趣**：平淡结局是毒药（原平局 39% 多为时钟拖尾）
   - **快输促重玩**：败局要快（中位第 5-6 回合，约 2.5 分钟），15 回合内必出结果
   - **惩罚要对行为定向**：极限压价、买卖不让利、囤积现金的"没有玩法"玩家要快速输掉——但**不能只靠加税**（"税太高了不合逻辑"，C4 重税方案已否）
3. **两轮 5000 局实验定案**（数据见第七、八节）：萧条税重税方案（C4，税70/红利20）总量达标但行为盲、叙事不合逻辑；**M套件**（维持费分级+通胀吞噬+救援门槛）以同等总量强度实现行为定向惩罚，定稿。

## 三、代码修复清单（实施前提，程序先做）

### P0 买地入账顺序 bug（一行换序 × 2 处，**必须最先落**）

- **位置**：`DiceRollController.cs` 人类玩家购买回调（≈L1722）与 `AIBuildingAction` AI 购买（≈L1814）
- **现状**（入账时 level 仍为 0，只记 400，买地净增财富仅 +80）：
```csharp
pd.cash -= BuildingData.BuyCost;
pd.propertyValue += data.TotalValue;   // ← 此时 data.level==0 → 只入账400！
data.level = 1;
data.ownerIndex = tokenIndex;
```
- **修复**（先升级再入账 → 记 800，净增 +480，与代码注释"买地净增财富+480"、模拟器口径一致）：
```csharp
pd.cash -= BuildingData.BuyCost;
data.level = 1;
pd.propertyValue += data.TotalValue;   // level==1 → 入账800，净增+480
data.ownerIndex = tokenIndex;
```
- **影响实证**：未修复的实机口径模拟 = 胜4.7/败44.3/平51.0；修复后 = v2.1 基线水平。**不修此 bug，本文档一切调参无效**。
- **验收**：①真机开局买一块地，面板"财富"应为 1300+480=1780（不是 1700）；②`[Prosperity]` Debug 日志的 min wealth 应含 480/块。

### P1 「伸出援手」并列匹配 bug

- **位置**：`DiceRollController.cs` ≈L1243-1255（`w == maxW2 && w != minW2` / `w == minW2` 值匹配）
- **现状问题**：并列最穷→人人有份（双份救济）；**全员 Wealth 相等（开局1300 即是）→ 无人被扣钱但全员+600/700，繁荣 50→73 直接冲进冲刺区**；并列最富→多人被劫。
- **修复规格**：第一遍循环找唯一索引（最富、最穷各取先遍历到的一个，与罗宾汉事件口径一致），第二遍只对这两个索引执行；若 `maxW == minW`（全员相等）→ 事件跳过，播报"【事件】市政库充盈，本轮无需救济"。
- **验收**：开局第一回合全员 1300 时触发该事件 → 无人扣钱、无人拿钱、出现跳过播报。

### P2 胜利线常量化 100 → 110

- **位置**：建议在 `MaxRounds`（L2785）旁新增 `private const int WinLine = 110;`
- **替换点**：`CheckGameEnd()`（≈L2309 `currentProsperity >= 100`）、`EndGameByRounds()`（≈L2326 同判定 + 文案"繁荣值达到100"）
- **理由**：胜利线扫描实测——线100胜率43%、线110→37%、线115→32%、线120→28%；拉到 123-125 也只压到 25-26% 且"临门一脚"挫败带膨胀到 27-29%。**线110+压红利20（M套件内含）组合落在 23.5%**，同时把临门一脚控制在 19%。
- **失败线 ≤20、回合上限 14 均不动。**

## 四、M套件机制规格（本版核心：「萧条经济」）

### 4.1 设计原理：行为闭环

游戏内已存在一套"行为传感器"，M套件只是把它的输出接进繁荣生存链：

```
玩家行为                    已有传感器（无需新代码）           M套件新增接线
─────────────────────────────────────────────────────────────────────────
砍价选「极限压价」人格卡  →  声望 -3（BargainState 已有）    → 声望<45：维持费翻倍 + 通胀起征点更低
砍价选「交个朋友/实价」   →  声望 +5/+3（已有）              → 免疫加征
声望低                    →  砍价公式吃亏（已有：rep/200）    → 声望<35：慈善家见死不救
囤积现金不出手            →  （无）                          → 危机通胀吞噬超额现金
让利/投资买入             →  现金流向他人（繁荣上涨）         → 现金轻，通胀咬不到
```

**「极限压价流」玩家的完整死亡螺旋**：压价成交 → 声望跌破 45 → 危机来临 → 双倍维持费 + 通胀起征点 450 专咬现金囤积 → 财富被抽干 → 自己沦为短板 → 声望<35 时慈善家不救 → 城市因他崩塌 → 败局播报点名。

### 4.2 参数表（M套件定稿值）

| 参数 | 值 | 说明 |
|---|---|---|
| 危机维持费 | 全员 −30/回合；**声望<45 → −60** | 萧条期市政服务费，恶名商人被民意抵制加倍 |
| 通胀吞噬 | 危机区回合末：现金 > **600** 的部分 −30%（单回合上限 250）；声望<45 起征点降至 **450** | 恶性通胀叙事：囤现金者购买力缩水；让利/投资者现金轻、天然免疫 |
| 救援门槛 | 慈善家 AI **不救声望<35 的短板** | 众叛亲离：压价史让恶名玩家在最需要救援时被抛弃 |
| 冲刺红利 | 冲刺区全员 **+20/回合** | 经济腾飞市政分红（轻推不白送） |
| 触发时机 | 回合末（最后一个玩家行动结束后），按**刚结束回合的区间**判定 | 只在危机/冲刺区收发，常规区不动作 |
| 通胀的钱去哪 | **蒸发（市政消耗），不转移** | 见 4.6——这是 5000 局实验换来的关键决策 |

### 4.3 实施规格（DiceRollController）

**插入点**：`NextTurn()` 内 `if (currentTurn == 0)` 分支——边境封锁倒计时之后、`// 计算繁荣值 UpdateProsperity();` 之前（≈L397），新增一行 `ApplyEconomyTick();`。这样收发完现金后由既有的 `UpdateProsperity()` 统一刷新繁荣、触发破产检查与播报。

**新方法**（可整段复制）：
```csharp
private bool[] surchargeWarned = new bool[4]; // 加征播报去重：每局每人只播一次

/// <summary>回合末经济收发（v2.2 M套件）：危机=维持费+通胀吞噬；冲刺=繁荣红利</summary>
private void ApplyEconomyTick()
{
    if (gameEnded) return;
    bool crisis = currentPhase == GamePhase.Crisis;   // 刚结束回合的区间
    bool sprint = currentPhase == GamePhase.Sprint;
    if (!crisis && !sprint) return;

    for (int i = 0; i < playerInfoPanels.Count; i++)
    {
        if (playerInfoPanels[i] == null) continue;
        var pd = playerInfoPanels[i].Data;
        if (!pd.alive) continue;
        bool infamous = pd.reputation < 45;

        if (crisis)
        {
            pd.cash -= infamous ? 60 : 30;                    // 维持费（恶名翻倍）
            int th = infamous ? 450 : 600;                    // 通胀起征点
            int ex = pd.cash - th;
            if (ex > 0)
            {
                int eaten = Mathf.Min(Mathf.RoundToInt(ex * 0.3f), 250);
                pd.cash -= eaten;                            // 蒸发，不转移
                BroadcastMsg($"【通胀】恶性通胀！{pd.playerName} 囤积的现金缩水{eaten}元", BroadcastBar.P1);
            }
            if (infamous && !surchargeWarned[i])
            {
                surchargeWarned[i] = true;
                BroadcastMsg($"【警告】{pd.playerName} 声望扫地，萧条中被民众抵制，维持费翻倍！", BroadcastBar.P0);
            }
        }
        else
        {
            pd.cash += 20;                                   // 冲刺红利
        }
    }
    if (crisis) BroadcastMsg("【危机】城市萧条，市政征收维持费", BroadcastBar.P1);
    if (sprint)  BroadcastMsg("【繁荣】经济腾飞，全城分红20元/人", BroadcastBar.P1);
    // 现金变动后由外层 UpdateProsperity() 统一刷新面板/繁荣/破产检查
}
```
注意：若维持费/通胀把某玩家现金打到负数，外层 `UpdateProsperity()` 内的 `CheckAllBankruptcies()` 会自然接手（强拍→出局→全灭），无需在此处理。

### 4.4 救援门槛（一行）

`TryRescuePoorest()` 找到 `poorest` 并通过 `minCash < 300` 判断后、执行交易前，加：
```csharp
if (poorData.reputation < 35) return; // v2.2 众叛亲离：恶名者无救援
```

### 4.5 败局点名播报（强烈建议，P5 演出素材）

`TryResolveBankruptcy()` 出局分支的 EndGame 文案按声望分岔：
```csharp
string endMsg = pd.reputation < 35
    ? $"{pd.playerName} 破产出局——为富不仁，众叛亲离，城市随之崩塌……所有玩家失败！"
    : $"{pd.playerName} 破产出局——城市失去了最后的经济支柱……所有玩家失败！";
```

### 4.6 关键决策记录：为什么是"蒸发"不是"转移"

5000 局实验证明：若把通胀/劝捐的钱**转给最穷玩家**（转移支付），等于给繁荣装了呼吸机——最穷者每回合 +300~400、繁荣指数瞬间 +11~15 点，败率从 47% 崩到 21%、平局涨到 48%，快输结构直接瓦解。**定向惩罚必须让钱蒸发**（通胀叙事：购买力消失于市场，而不是塞进某个口袋）。这条不要"优化"成转移支付。

## 六、UI 联动（短板可见性）

### 6.1 繁荣面板 + 短板同屏（用户拍板：跟繁荣指数一起显示）

- **格式**：`繁荣指数 63 ▲｜当前短板：莉兹（财富1640）`
- **实现**：`prosperityText` 保持现有刷新（实时数字）；新增一个 `bottleneckText`，**只在回合末刷新**（与 `ApplyEconomyTick` 同一位置调用）。不能每次资金变动都刷——短板身份实测每局换手 6.3 次、65% 的局 4 人全部轮到过，逐笔刷新会闪烁到不可读。
- **并列处理**：多人并列最穷时显示先遍历到者（与济贫事件口径一致，v1 从简）。

### 6.2 声望预警（让玩家提前看见惩罚逼近）

`PlayerInfoPanel.UpdateDisplay()`：`reputationText` 颜色按声望分级——`rep < 45` 变红（建议 #A61E19 系），否则保持现有绿色 #477524。玩家看一眼面板就知道"我在被民意盯着"。

### 6.3 背景数据（为什么需要短板标记）

繁荣=最穷玩家财富/26 的"木桶规则"下，短板身份高度动态（换手 6.3 次/局、时间占比四人均衡 23-28%），但**目标函数其实不变**——"把全场最小财富抬到 110 线"。UI 标记解决的是"轮转可读性"，不是新机制。

## 八、程序实施顺序与验收流程

**Step 1 —— 修复回归（P0/P1）**
1. 按第三节修 P0（两处换序）、P1（唯一索引化）
2. 编译 0 错误；真机开局买一块地，面板财富 1780（+480）
3. `python3 tools/pace_sim_v22.py --legacy` → 应落在 **胜36.5/败26.3/平37.3 ±5%**（确认模拟器与修复后实机口径一致）

**Step 2 —— M套件 + 胜利线（P2）**
1. 按第三、四节落 `WinLine=110`、`ApplyEconomyTick()`、救援门槛、播报文案（第五节）
2. `python3 tools/pace_sim_v22.py` → 应落在 **胜23.5/败45.8/平30.7 ±5%**，败局中位第 6 回合

**Step 3 —— 真机试玩验收（5-10 局，个体行为观察）**
- [ ] 极限压价 5 局以上：声望面板是否如期跌破 45 变红？维持费是否翻倍？
- [ ] 囤现金打法：危机中是否被通胀持续吞噬、播报是否成立？
- [ ] 让利打法：是否能稳定把繁荣推过 110 赢下？
- [ ] 恶名玩家破产：败局是否点名"众叛亲离"？慈善家是否真的不救？
- [ ] 体感：输的局是否"输得明白"（知道败因）、是否想立刻重开？

**三段式验证声明（诚实边界）**：
1. **机制推理成立**——M套件每一环都接在已有系统上（人格卡声望、砍价公式、慈善家AI），无新造轮子；
2. **总量已验证**——5000 局×多轮实验，胜负分布/节奏/时长全部达标；
3. **个体行为差异待真机确认**——模拟器对真人砍价行为建模有限（sim 中玩家0踩到他人地块仅 ~0.5 次/局、人格卡选卡公式简化），声望轨迹与短板归属的个体体验**必须**以 Step 3 试玩为准。若试玩发现恶名惩罚过重/过轻，用第七节手柄微调后重跑 Step 2 对照。
